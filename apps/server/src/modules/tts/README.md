# TTS 模块架构设计

本文记录 `apps/server/src/modules/tts` 的现状和建议的演进方案。**目标目录和接口是设计提案，尚未全部实现**；文件名、类型名和装配方式可以在实施时根据实际代码调整。

目标是在保持现有对外行为的前提下，明确配置管理、语音生成和供应商接入的边界，让业务流程不依赖 Express、Prisma 或具体供应商协议。

## 1. 模块职责和边界

TTS 模块负责：

- 管理 TTS 服务配置，校验、保存、读取、更新和删除配置，并提供不包含 API Key 的管理视图。
- 解析语音服务，区分浏览器朗读和服务端合成；对服务端合成执行输入校验、取消、超时和资源控制。
- 通过适配器接入 Speaches、百炼和 OpenAI 兼容接口，将供应商结果转换为 World 所需的音频格式。
- 查询 Speaches 的模型和音色，并提供部署默认语音的就绪状态。

TTS 模块不负责：

- 决定 Agent 在什么时候说话、哪些玩家能听到、音频片段如何缓存或分发；这些属于 World 和 Agent 的业务流程。
- 浏览器端的语音合成和播放；TTS 只提供浏览器朗读所需的参数。
- 模型安装和容器启动；模型发现与就绪检查是只读操作。
- 管理 HTTP 认证策略；路由由服务端管理入口保护。

## 2. 当前问题

1. **已初步拆分**：`services/tts.service.ts` 原先同时处理配置 CRUD、供应商校验、模型发现、合成、并发控制和跨模块通知。现在配置规则、配置管理、模型发现和语音执行分别位于 `domain/voice-service-validation.ts`、`services/voice-service-management.service.ts`、`services/speech-models.service.ts` 和 `services/speech.service.ts`；`TtsService` 是唯一应用服务类，`composition.ts` 的 `createTtsService()` 装配默认依赖并创建 `ttsService`。
2. **已初步处理**：World 通过 `ttsService.resolveSpeech()` 统一解析未绑定、空绑定和已保存服务。未绑定默认语音仍不经过已保存服务的进程内并发限制；是否统一限额需另行评估。
3. **已初步处理**：`ResolvedSpeech` 区分浏览器朗读和服务端合成；World 根据分支播放。配置变更仍依赖进程内通知取消相关任务，不提供跨进程或提交与通知之间的原子保证。
4. **已初步处理**：服务端供应商协议已拆分到 `adapters/`，由工厂选择 Speaches、百炼或 OpenAI 兼容实现；配置规则仍位于领域校验中。
5. 删除前检查借助同步事件和监听器抛错实现，检查条件不容易从删除流程中看出；数据库外键另行保护持久化引用。
6. **已初步处理**：默认模型就绪检查与 `core/audio/speaches-models.ts` 共用受限响应读取，保留各自的解析和错误契约；默认检查不代表所有已配置服务的状态。

## 3. 目标目录

目录遵循项目现有的 `domain/`、`services/`、`persistence/`、`routes/`、可选 `ports.ts` 和模块门面约定。以下是完整的目标职责分布，不要求第一阶段一次性创建所有文件。

```text
apps/server/src/modules/tts/
├── README.md                                     # 模块现状、职责边界与演进方案文档
├── index.ts                                      # 模块公开门面
├── ports.ts                                      # 应用层需要的存储、合成、模型查询和协作契约
├── composition.ts                                # 模块内部装配默认实现；路由仍保留零参工厂
│
├── domain/                                       # 无网络、数据库和文件 I/O 的模型与规则
│   ├── voice-service.ts                          # 配置模型、类型、脱敏视图和播放方式
│   ├── voice-service.test.ts                     # 配置模型、脱敏转换与播放方式单元测试
│   ├── voice-service-validation.ts               # 当前服务类型、模型与显式音色的校验规则
│   └── voice-service-validation.test.ts          # 配置输入校验单元测试
│
├── services/                                     # 组织业务用例，不处理供应商 HTTP 细节
│   ├── voice-service-management.service.ts       # 配置 CRUD、数量限制、删除前检查和变更通知
│   ├── voice-service-management.service.test.ts  # 配置管理、删除保护与通知用例单元测试
│   ├── speech.service.ts                         # 解析播放方式、合成、取消、超时和并发控制
│   ├── speech.service.test.ts                    # 播放解析、合成调度、超时取消与并发控制单元测试
│   ├── speech-models.service.ts                  # 模型发现；目标还包括默认服务就绪状态用例
│   └── speech-models.service.test.ts             # 模型发现测试；目标还包括默认语音就绪状态
│
├── adapters/                                     # 外部服务和技术能力的适配
│   ├── speech-adapter-factory.ts                 # 根据已校验的类型创建服务端合成适配器
│   ├── bounded-response.ts                       # 可选：共享响应限长读取及释放资源
│   ├── speaches-tts.adapter.ts                   # Speaches 合成协议（Piper 是模型，不是 HTTP 服务名）
│   ├── speaches-tts.adapter.test.ts              # Speaches 请求、超时、响应大小与 WAV 校验测试
│   ├── compatible-tts.adapter.ts                 # OpenAI 兼容的 /audio/speech 协议
│   ├── compatible-tts.adapter.test.ts            # OpenAI 兼容合成协议、错误映射与音频标准化测试
│   ├── bailian-tts.adapter.ts                    # 百炼请求、响应和音频地址处理
│   └── bailian-tts.adapter.test.ts               # 百炼协议、音频 URL 限制与音频标准化测试
│
├── persistence/                                  # 存储技术适配
│   ├── database-voice-services.ts                # Prisma、密钥加解密、事务和错误映射
│   └── database-voice-services.test.ts           # 数据库持久化、密钥加解密与事务约束测试
│
└── routes/                                       # Express 入站适配
    ├── tts.routes.ts                             # defaults、models、services 和 preview
    └── tts.routes.test.ts                        # TTS 路由输入、状态码与请求断开取消测试
```

Speaches 模型查询还供 ASR 使用，应优先复用 `core/audio/speaches-models.ts` 或其底层 HTTP 能力。默认就绪检查与管理界面的模型发现有不同的解析和错误行为，不能直接互换；第 6.3 节说明兼容性要求。音频校验和转换可继续复用 `core/audio/pcm-wav.ts` 与 `core/audio/normalize.ts`。

供应商适配器可以共用限长读取响应体、释放 reader 等辅助逻辑，但各自保留响应大小上限、供应商错误分类与处理方式。不能将可能回显密钥或输入文本的上游错误原文直接返回给调用方。辅助文件是否需要创建，取决于拆分后是否确有重复逻辑。

各目录按职责创建，不为了形式增加单文件空目录或一一对应的接口。测试与被测文件就近放置；跨模块集成测试放在 `apps/server/test/` 或项目现有的集成测试位置。

## 4. 各层依赖和公开边界

```text
HTTP 路由 ──────┐
World / Agent ──┼──> TTS 公开用例 ──> TTS 领域规则和端口
能力聚合入口 ───┘                          ↑
                               数据库、供应商、模型查询适配器
```

- `domain/` 负责语音配置、播放方式及不涉及外部 I/O 的规则；不依赖 Express、Prisma、`fetch` 或其他业务模块。
- `services/` 编排用例并依赖端口；不直接创建 Prisma 客户端或供应商 HTTP 实现，也不读取请求和响应对象。
- `adapters/`、`persistence/` 实现端口；它们可以使用 `fetch`、Prisma、环境配置和音频转换等技术能力。
- `routes/` 负责 HTTP 输入、状态码、音频输出和请求断开时的取消；管理鉴权仍由服务端挂载层执行。
- `composition.ts` 负责创建并连接默认实现。`createTtsRouter()` 继续保持项目要求的零参公开工厂；内部测试可以直接构造应用服务并传入替身。
- `index.ts` 只公开路由工厂和其他模块需要的应用能力与类型；World、Agent 和 ASR 不直接导入 `SpeachesTtsAdapter`、Prisma 仓储或供应商适配器。

不要求抽象掉所有公共库，也不为了使用端口而包装每个函数。端口用于隔离应用流程真正依赖的外部能力，尤其是持久化、供应商调用及跨模块删除协调。

## 5. 主要模型与端口

以下接口是说明边界的示意，并非已存在的 API。实际参数和错误类型以实施时的兼容性验证为准。

### 5.1 配置和管理视图

- 内部配置包含 `id`、类型、连接参数、模型、音色、语速及服务端使用的密钥。
- 管理视图包含 `hasApiKey`，不返回密钥；更新时保留当前“地址和类型未变可复用已有密钥”的行为。
- 业务调用方如果只需要确认配置存在，应使用窄接口，例如 `assertVoiceServiceExists(id)`；不应为了校验存在性取得完整的解密配置。
- 浏览器、Speaches、百炼和兼容接口的配置可在内部逐步用 `type` 区分；外部请求和数据库格式不必随内部类型改动。

### 5.2 播放方式

当前 `ResolvedSpeech` 使用两个明确的分支：

```ts
type ResolvedSpeech =
  | {
      kind: 'browser';
      voice: { voice: string; speed: number; voiceLanguage?: string };
    }
  | {
      kind: 'server';
      synthesizer: SpeechSynthesizer;
    };
```

浏览器分支只提供客户端朗读参数；服务端分支提供可取消的合成能力，不向调用方暴露供应商配置或密钥。`SpeechSynthesizer` 只表示服务端合成能力。

当前沿用**执行时读取**语义：解析时读取配置以决定播放分支；服务端执行时再次读取当前配置。同一服务端分支解析后如果更新了模型或音色，执行时使用更新后的配置；如果改成浏览器模式则拒绝服务端合成，删除后则报告配置不存在。浏览器分支持有解析时的朗读参数，World 收到配置变更通知时取消相关任务，避免通知到达后继续发送旧参数。

配置写入提交后才发出进程内通知，因此提交与通知之间仍有竞态；取消也不能保证供应商尚未收到请求或产生费用。这里不保证跨进程一致性或严格撤销；如需更严格语义，应单独设计版本检查或受控执行入口，并覆盖对应交错。

World 的绑定有三种需要区分的状态：`undefined` 走未绑定的默认路径；非空 ID 指向已保存配置；空串由 Agent 协调器用于关闭语音或聊天权限时的绑定。这三种状态均由 `ttsService.resolveSpeech()` 处理。空串返回调用 `ttsService.synthesize('')` 的兜底闭包，但正常执行还受 World 的说话条件和取消检查影响；不应假定它一定会发起合成。未绑定路径由 TTS 内部创建默认语音合成器。它与数据库中的 `local-default` 配置不同，不能擅自合并。

### 5.3 应用层依赖

| 契约               | 使用者               | 责任                                                                   |
| ------------------ | -------------------- | ---------------------------------------------------------------------- |
| 配置仓储及事务     | 配置管理、语音生成   | 读取配置；在事务中计数、创建、更新和删除，保留密钥保护及数据库约束     |
| 服务端语音合成     | 语音生成             | 根据已校验配置和文字生成标准音频，支持取消                             |
| 供应商适配器工厂   | 语音生成             | 选择已支持的服务端供应商实现；浏览器分支不创建服务端适配器             |
| Speaches 模型查询  | 模型发现             | 查询给定连接的已安装模型和音色，可取消且有响应大小与时间限制           |
| 删除前使用状态检查 | 配置管理或上层协调器 | 检查运行中绑定及未完成的更新等进程内状态；持久化引用仍由数据库外键兜底 |
| 变更通知           | 配置管理             | 配置提交后通知相关运行时取消或刷新；明确通知失败不能被误报成数据库回滚 |

端口由消费它的应用逻辑定义。`ports.ts` 可以先集中声明，只有当接口增多且有明确归属时再拆分。

## 6. 关键流程

### 6.1 管理配置

```text
Console → 管理鉴权 → TTS 路由 → 配置管理用例
                                    ├─ 校验当前配置
                                    ├─ 仓储事务：读取 / 计数 / 写入
                                    └─ 提交后通知配置变更
```

删除前的同步检查和删除后的通知应分别表达。数据库中 Agent 引用的 `onDelete: Restrict` 仍是持久化引用的最终约束；运行中的绑定和正在更新的状态不在数据库外键的保护范围内。

重构时不能简单删除现有两次 `tts.service.removing` 检查：它们位于事务前和事务内。需要先梳理 Agent 保存、绑定和删除的并发时序，设计可证明安全的协调方式，再调整实现。进程内检查不自动提供跨进程保证；如果未来支持多实例，需要另行设计跨进程协调。

检查方具有不同的生命周期：Agent 编排器注册并释放自己的守卫，World 房间在创建时注册、销毁时释放守卫；Provider 删除也使用类似的同步事件机制。若改成显式协作，设计必须支持动态加入和清理检查方，并覆盖初始化失败、关闭、重复注册等情况。现有事件总线已经支持动态注册，显式协调器、守卫注册器或保留现有机制均可评估；新增注册表本身不能解决检查后出现新绑定的竞态。先明确并发保证和生命周期，再决定是否替换现有机制。

### 6.2 World 语音

```text
World → 按 Agent 绑定解析语音方式
          ├─ browser → World 发送文字和朗读参数，由客户端播放
          └─ server  → TTS 用例控制执行 → 供应商适配器 → 标准 WAV
                   → World 按原有规则缓存和分发
```

World 保留自己的队列、收听范围、片段缓存与访问检查。TTS 负责合成执行的资源约束；限额是按进程、服务还是供应商划分，需要明确配置和产品语义。现有通过 `ttsService` 的服务端合成最多两并发，而未绑定的默认语音工厂创建的合成器不经过该计数。是否改变这一差异需要单独评估。

当前 `ttsService` 校验文字并设置 60 秒超时；`SpeachesTtsAdapter` 自身也有这些保护，直接使用的默认路径依赖其实现。将校验和超时集中到应用用例之前，必须确认默认路径与所有其他调用都经过该用例，并验证原有取消、错误和超时行为。供应商适配器仍可保留与协议或资源安全有关的必要检查。

### 6.3 模型发现和状态

- 管理界面模型发现使用指定连接，遵守现有密钥复用和连接校验规则，只读取服务端已安装模型。
- 默认就绪状态检查部署默认地址和默认 Piper 模型，不等同于任意用户配置的就绪状态。
- `/voice/capabilities` 目前由 ASR 路由聚合；可以先保持原路径和响应，通过 TTS 公开用例获取状态。未来若迁移到独立语音能力聚合入口，应单独评估路由、认证和兼容性。

默认就绪检查与模型发现共享底层限长响应读取，但保留各自的解析和错误行为：

- 默认就绪检查只使用 `data[].id`；测试覆盖有、无和不匹配 `task` 的记录。`SpeachesModels.list()` 只保留 `task` 与请求匹配的记录，还对模型和音色字段做更严格的解析。直接替换可能使原本就绪的模型被忽略，或使默认检查因无关字段不合法而失败。测试还覆盖无关字段不合法；实际 Speaches 部署返回什么字段需要另行验证。
- 默认检查将异常转为固定的 `available: false` 和 `reason`，模型缺失也有独立文案；共享查询的错误更加细分。保留 `/voice/capabilities` 对外的状态与文案，不能让内部 `503` 或 `502` 的差异直接改变调用方看到的结果。
- 两条路径复用 1 MiB 限长读取和 reader 清理，分别保留超时、取消、鉴权及错误映射；ASR 模型发现继续使用原有解析策略。

## 8. 分阶段实施和验收

1. **固定现有行为**：梳理配置 CRUD、默认语音、浏览器模式、模型发现、取消和删除保护的调用链；补足能够覆盖关键边界的测试。
2. **统一调用入口**：World 已通过公开解析能力处理默认语音、空绑定和配置语音，保持原有默认路径及并发差异；Agent 配置存在性检查等窄接口仍待整理。
3. **拆分用例与模型**：已区分浏览器和服务端播放方式，拆出配置管理、语音执行及模型发现，仓储与模型查询通过端口注入，并保留现有 HTTP 和数据格式；默认就绪判断的服务归属与删除协作仍可后续整理。
4. **整理适配器**：已拆分供应商协议并复用 Speaches 模型响应的限长读取，保留各查询的解析与错误契约，以及密钥、URL、超时、取消和音频格式限制。
5. **明确删除协作**：验证并发时序后引入显式检查和提交后通知；保留数据库外键、事务与运行时取消保护。
6. **收窄模块门面**：移除外部对具体实现的依赖，并检查跨模块引用和依赖方向。
